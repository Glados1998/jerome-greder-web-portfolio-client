# Payload 3.93 upgrade

All six direct Payload packages are pinned to `3.93.0`. Keep their versions aligned when upgrading.
This update starts from the schema generated by this repository's `3.85.1` configuration.

## Runtime and configuration

Payload requires Node `^22.23.4 || >=24.22.1`. `.nvmrc` selects `22.23.4`; configure CI and hosting
to use a compatible runtime too. The global Node installation is not changed by these files.

The project now declares ESM with `"type": "module"`, and PostCSS configuration uses
`postcss.config.mjs`. This also lets Payload's standard CLI load the TypeScript configuration.

```bash
nvm install
nvm use
npm ci
npm run payload -- generate:types
npm run payload -- generate:importmap
```

## Database selection

- Development, tests, and the default Payload CLI use `DATABASE_URI_DEV` (or the existing localhost
  fallback when it is unset). Development accepts loopback hosts only and uses a plain local
  PostgreSQL connection.
- `NODE_ENV=production` uses `DATABASE_URI`, which is required. Production keeps verified TLS and
  reads the CA from `RDS_CA_PEM`.
- `NEXT_PUBLIC_API_URL_DEV` controls frontend API requests; it does not select the PostgreSQL database.

Use `NODE_ENV=development npm run payload -- migrate:status` to explicitly inspect local migration
status. A local database managed by development push should continue using push; do not also apply
the same schema changes through migrations. Test migrations against a separate database clone at
the expected starting schema.

The local metadata check on 2026-11-06 found development-push history and a schema older than the
upgrade's starting point: `users_sessions`, `project_git_links`, and `payload_kv` were missing,
along with earlier project/programming-tag fields. Neither new column nor any of the three new
indexes was present. The check used a read-only connection and made no schema changes.

For normal local development, use `npm run dev` and let Payload synchronize the local schema;
review any rename/drop prompts and keep a backup if the local data matters. The upgrade migration
is not a replacement for those earlier application schema changes. For a faithful migration test,
use a separate copy of the actual pre-upgrade production database.

## Incremental database migration

`src/migrations/20261106_004100_payload_3_93.ts` contains the schema difference generated offline
from the old and new configurations:

- Nullable `users.reset_password_requested_at` for password-reset throttling.
- Nullable `media._objectkey` for storage metadata. Existing media filenames are preserved.
- Parent-ID indexes on `services_locales`, `project_locales`, and `values_locales`.

Its JSON snapshot records the resulting schema for future `migrate:create` commands.
This is an incremental migration for an existing database, not an initial schema for an empty one.
The repository had no previous migration files, so compare the deployment database with the
expected old schema before applying it. No live database was inspected to generate this migration.

## Deployment sequence

1. Back up the existing database and restore it to a disposable clone.
2. Point `DATABASE_URI` and its TLS settings at the clone, then run in production mode:

   ```bash
   NODE_ENV=production npm run payload -- migrate:status
   NODE_ENV=production npm run payload -- migrate
   ```

   If Payload reports that development schema push was used, reconcile the clone's migration
   history and actual schema before proceeding. The migration expects the two new columns and
   three indexes to be absent; it does not reset or recreate existing tables.
3. Check admin login, password reset, localized content, rich-text content, and an S3 upload and
   replacement against the clone and a test bucket.
4. During deployment, with the compatible Node runtime and verified target database configured,
   run `NODE_ENV=production npm run payload -- migrate` before starting the upgraded application. Migration execution is a separate
   step; it is not attached to `npm run build` or application startup.

The `down` function removes the new columns and their values. After new uploads use `_objectKey`,
prefer a coordinated database/storage backup restoration to dropping that metadata.

## Verification scope

The SQL was tested with an in-memory PostgreSQL engine initialized from the old generated schema.
Both `up` and `down` ran successfully, existing user/media rows survived, the two columns and three
indexes matched the generated difference, and `up` succeeded again after rollback.

This does not verify the schema of the hosted database, live authentication, or S3 behavior.
